# Session — 2026-08-18 14:48

**Branch:** main · **Commit:** `0c67263`

## Summary

Built **Linear Half Toner** from nothing: a browser app that turns a picture into a line
halftone where line width encodes tone, then converts that width into cut depth through
V-bit geometry so it can be carved on a CNC router. Delivered a working v1, renamed the
folder and added docs, produced a prioritised list of 14 improvements at the user's
request, then implemented and verified all 14. The app roughly tripled in size (60 KB →
180 KB) and gained a shared geometry engine that runs in a Web Worker.

## What changed

**New project `Linear Half Tone/`** — one self-contained HTML file, no build, no
dependencies, nothing uploaded. Matches the repo's existing per-project convention.

- Five-step workflow: Source → Correct → Pattern → Tool → Export (`index.html`)
- Image correction runs *before* halftoning, as the user specifically asked: crop with
  draggable handles, rotate/flip, nine greyscale conversions, levels with live histogram
  and auto-levels, draggable tone-curve spline, exposure/brightness/contrast/gamma,
  posterise, median denoise, blur, unsharp mask, and paintable masking
- Nine pattern families: parallel lines, cross hatch, wavy, concentric, spiral, radial,
  contour (marching squares), dot screen (Floyd–Steinberg), stipple/TSP (Lloyd relaxation
  plus nearest-neighbour and windowed 2-opt tour)
- Up to three tools per job, each with its own pattern, angle, pitch, tonal band, mask
  region and feeds — the standard roughing-plus-detail V-carve workflow
- Export to SVG (variable-width outlines, 1 unit = 1 mm), DXF (R12 POLYLINE and R2000
  LWPOLYLINE, with per-vertex widths), and G-code (GRBL / Mach3 / LinuxCNC / Marlin, arc
  fitting, laser power mode, bed tiling, per-tool files, multi-pass)
- Toolpath optimisation: Douglas–Peucker simplification over position *and* width jointly,
  plus nearest-neighbour travel ordering
- Acceleration-aware run-time estimate using GRBL's junction-velocity model with
  forward/backward passes and a controller block-rate ceiling
- Carve simulation: shaded relief rasterised from actual cut depths
- Web Worker pipeline, 60-step undo/redo with A/B snapshot compare, tool library,
  159-setting presets

**Documentation** — `README.md` covering the V-bit maths with a worked depth table, the
five-step workflow, per-format CAM import notes, and the settings that matter most.

**Repo hygiene** — `.gitignore` now excludes `NOVELTECH/` and `*.nc` (see Decisions).

## Decisions

- **Width modulation is the V-carve mode, and the maths is stated explicitly.** For a
  V-bit of included angle `A`, `w = 2·d·tan(A/2)`; a tapered engraver adds its tip
  diameter. The app inverts this so every line width becomes a depth, and caps usable
  width by `min(cutter diameter, 2·maxDepth·tan(A/2))`. Verified exact across 30/60/90°
  V-bits and a 20° tapered engraver.
- **SVG/DXF outlines are the recommended route, not the G-code.** Handing closed
  variable-width outlines to VCarve/Aspire/Fusion means the CAM derives depth from shape
  width — its depth model, not ours. Direct G-code exists because the user asked for it,
  but the UI and README both push the CAM route first and warn to dry-run.
- **Single self-contained HTML file, not split into css/js.** The user was offered the
  split and chose against it; it keeps the app portable and matches `VECTOR-EDITOR`.
- **Folder is `Linear Half Tone`, app is titled `Linear Half Toner`.** The user renamed
  the folder to the shorter form; the app keeps the original name they specified. Left
  deliberately inconsistent rather than guessing which one they wanted everywhere.
- **`NOVELTECH/` is excluded from version control.** It is a *separate git repository*
  with its own GitHub remote and history (CNC polygon-cutting work, 6.3 MB, 265 files).
  Committing it would create a gitlink pointing at a commit this repo's remote does not
  have, which breaks every clone — git warns about this itself. Gitignored rather than
  committed.
- **`*.nc` is excluded.** `test-target-halftone.nc` at the repo root is 770 KB of
  generated output from the app (spiral pattern, 90° V-bit ⌀12 mm — the user exercising
  it). Generated toolpaths are build artifacts, not source.
- **Session summary lives in `Linear Half Tone/sessions/`, not root `sessions/`**,
  following the convention set in `e35bf0f`: root is reserved for cross-project work, and
  this session was entirely about one project.

## Open threads

- **The carve simulation was never checked visually.** The Browser pane stopped
  compositing frames partway through verification, so it is confirmed only numerically
  (1000×750, luminance spread 18–237, caching correct). Worth a human look — it is the
  one feature where "the numbers are right" is weakest evidence.
- **Simplification does not reduce cutting time on straight-line patterns.** Junction
  speeds were already at full feed, so removing collinear points changes file size and
  block count but not kinematics. It *does* halve run time on a block-rate-limited
  controller (1489 s → 692 s at 20 blocks/s). The README states this honestly; do not let
  it drift into an overclaim.
- **`localStorage` is unavailable when the page is served from a `data:` URL**, so the
  tool library silently falls back to built-in defaults in that context. Fine on `file://`
  and on Pages, but it means the library could not be verified as actually persisting.
- **Root `index.html` still redirects straight to `VECTOR-EDITOR`.** Linear Half Toner is
  not reachable from the published site. Turning the root into a launcher for both was
  offered and not taken up.
- Nothing has been carved. Every claim about machine behaviour is derived from the
  geometry and the timing model, not from a physical test cut.
