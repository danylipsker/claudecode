# Session — 2026-10-05 05:31

**Branch:** main · **Commit:** 7287fa3 (Hyper ESP32), plus this summary

## Summary
One long session, 4–5 October 2026, that built **Hyper ESP32**, the 17th Hyper app. Dany asked for an app that
concentrates everything about Espressif's ESP32 family: every chip with its virtues and limits, a way to pick the
right one by describing a project, the boards of other makers, pinouts, programming in C++, Python and
Scratch-style blocks, displays and touch GUIs, state machines — "and any existing topic out there". He left the
form to me ("if you think making this app as an HYPER-ESP32 is a better approach, so be it"). It ended complete:
603 pages, 626 programs, 456 simulations, five labs, every check passing, and — a late discovery — the C++
programs really compiled on this machine.

## Decisions
- **Built as a Hyper app, not a standalone one.** The engine already gives pages, simulations, formulas, search,
  progress and cross-links; a new app would have re-made them. Dany's empty folder `ESP32-ABILITIES` was left
  untouched.
- **Facts live in a catalogue; pages quote it.** Chip, pin and board facts were researched once against primary
  sources and written to two data files; writers were told never to type such a fact from memory. To correct a
  fact, correct the data file. The generator that built those files lived in the session's scratch folder and
  is not in the repo: the files are edited by hand from now on.
- **Programs are written for the current software** (Arduino core 3.3.x, MicroPython 1.29, ESP-IDF 5.5/6.x,
  LVGL 9, ArduinoJson 7), from a verified crib (`API-CRIB.md`); its Appendix C records every correction found
  while writing and compiling, and overrides what stands earlier in it.
- **Compile, do not just review.** Late in the session I found the Arduino IDE's `arduino-cli` and the ESP32
  core installed here (I had assumed there was no compiler). Building all 620 C++ programs took about five
  hours of machine time and found a dozen real errors that reading had missed: a wrong argument type for I2S,
  variables named `RX`, `TX`, `T0`, `BOOT_PIN`, `index` that clash with the core, colour names from an older
  Arduino_GFX, a call removed in ArduinoJson 7, an attribute the Arduino build rejects. All fixed. Final count:
  543 build (7 as one part of a sketch), 71 need a library that is not installed here, 2 need a newer core,
  4 are for other boards, none fail.
- **Nothing was installed and the sketchbook was not touched.** The Arduino sketchbook is under OneDrive; the
  compile tool only reads it, and chooses the right copy when a library is there twice.
- **Where a newer call broke on the installed core, the portable form was used** when one exists (the built-in
  CA bundle through `setCACertBundle`), and the page says which core it needs when none does (the two Matter
  helper calls need core 3.3.12).
- **MicroPython was checked as far as it can be without a board**: syntax by Python, and every module and
  attribute name against the MicroPython 1.29 source (two mistakes found and fixed).
- **One writer per topic, in parallel**, each handed a brief, the authoring guide and notes for its topic, and
  each reporting what it was unsure of. Their reports exposed real bugs in the catalogue and engine (the pin
  planner, a tag rule that marked every Heltec board "cellular", nested pin groups lost, battery self-discharge)
  which were fixed as they came in.
- **Safety and law are part of the text**: mains warnings, lithium cells, radio rules, camera and microphone
  consent, security pages that are defensive only.

## Open threads
- **Nothing was run on hardware.** A program that builds is valid C++ for that core; whether it does what the
  page says is unproven. MicroPython programs were never executed.
- **71 C++ programs were not built** because their library is not installed here (PubSubClient 20, RadioLib 5,
  OneWire 5, LiquidCrystal_I2C 4, AsyncTCP 4, M5Unified 3 and others — the list is in `COMPILED.md`).
  Installing them writes into Dany's sketchbook, so it is his call; then
  `node HYPER-CORE/tools/compile-esp32.js --work <dir> --report` builds only what has not built.
- **The installed ESP32 core is 3.3.7; the programs' baseline is 3.3.12.** Two Matter programs need the update.
  Five Arduino_GFX programs could not be built because the installed Arduino_GFX 1.6.4 itself does not build
  with core 3.3.7.
- **Dany's sketchbook has two problems he may want to fix**: an old duplicate `Adafruit_GFX` folder that the
  compiler picks first, and a `LiquidCrystal` folder whose files cannot be read (probably cloud-only).
- **Typical figures written from memory.** Each writer listed facts it was not sure of (part ratings, timings,
  third-party library calls, regulation dates). The ones a compiler or the MicroPython source could settle
  were settled; the rest were not checked one by one. The reports are in this session's transcript only.
- **A full compile run takes longer than the two-hour limit of a background command**; it is resumable, and
  LVGL and BLE programs are the slow ones.
- The writers used up the **weekly Sonnet limit** part-way (18 agents stopped at 473 of 603 pages); they were
  resumed after Dany said to try again.
- Dany asked for a `git push` of commit `1bd5e2c` to a `refs/claude-teleport/…` ref for a move to the cloud; the
  session's permission classifier blocked it and it was not done.
