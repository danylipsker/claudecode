## What changed

- **Worm gear: full integration.** `GearFamily.Worm` end to end — `server.py` outline/
  export/mesh commands, C# `GearParameters`/`PyEngine` wiring, the mosaic's Worm card,
  worm-specific inputs, live 3D thread render, derived-values panel. Found and fixed an
  uncatchable `StackOverflowException` at app startup: two independent `RadioButton` pairs
  (helical's and worm's hand toggles) shared one WPF `GroupName`, and two same-named,
  independently-bound-true radio buttons drive WPF's own Checked/Unchecked sync into
  unbounded recursion. Found by bisecting `GearPanel.xaml` against the `--uismoke` smoke
  test, which reproduces the crash in under a second.
- **Bevel gear: two real geometry bugs, both now fixed** (`involute.py`, `build_gear.py`).
  1. `single_tooth_polygon`'s blank was sized `1.05x` the addendum radius instead of
     exactly the addendum radius — a leftover mix-up with an unrelated margin concept —
     so nothing capped the tooth tip at the true addendum circle. Every tooth's tip sat 5%
     too far out, and since involute flanks narrow going outward, that read as a sharp
     point instead of a flat tip: 20 of them made the whole gear look like a spiky
     pinwheel, not a gear.
  2. Even after that fix, the built solid measured `is_manifold = False`. A bevel tooth's
     toe/heel boundary is a genuinely non-planar 3D curve, and `make_loft(ruled=True)`'s
     automatic end-capping silently fails on that — it still returns something with a
     plausible-but-wrong volume, so nothing raises. Fixed by capping both ends explicitly
     with `Face.make_surface` (accepts non-planar boundaries) before sewing into a Solid.
     That surfaced a third issue: fusing all `z` now-correct teeth onto the blank isn't
     reliably robust in OpenCASCADE either (a sequential fuse loop silently corrupts
     partway through for some gear sizes; a single N-ary fuse fails differently on
     others). Fixed by not fusing at all — the solid is a `Compound` of the blank plus
     each individually-manifold tooth, the same tradeoff worm gears already made for the
     same underlying reason.
  Regenerated `thumb_bevel.png` (the old one visibly showed the broken shape).
- **Spur/helical/worm checked for the same bug class, none found.** Built several
  z/module/bore/helix/hand/starts combinations of each, checked `is_manifold` + body
  count + exact addendum-radius agreement + an actual render. All clean. Added permanent
  regression tests for all three anyway (`test_spur_and_helical_solids_are_manifold_single_bodies`,
  worm's `test_full_solid_bodies_are_all_manifold_with_correct_count`), since "only bevel
  had this coverage" was exactly the gap that let its bugs ship unnoticed.
- **SolidWorks add-in: two real registration bugs fixed** (`register-addin.ps1`,
  `SwAddin.cs`). Actually launched SolidWorks and checked whether the add-in loads, rather
  than trusting the registration script's own success message.
  1. The script's default DLL path pointed at `bin\Debug\net48\...`, but the project
     builds x64-only — real output is `bin\x64\Debug\net48\...`. A stale DLL happened to
     still exist at the wrong path (predating `PlatformTarget=x64`), so `Test-Path` didn't
     catch it and the script silently registered an old, outdated copy. Fixed the default;
     deleted the stale folder.
  2. `Register-ComClass`'s `Write-Output "Registered $ProgId -> $clsid"` line polluted its
     captured return value — PowerShell folds a function's entire output stream into a
     capture, not just its `return` — turning `$addinClsid` into a 2-element array.
     String-interpolating that array into the `AddIns`/`AddInsStartup` key paths joined it
     with a space, creating a key literally named `"Registered ... -> {guid} {guid}"`
     instead of the clean `{guid}` SolidWorks looks for. The add-in has therefore never
     actually been discoverable via Tools > Add-Ins in any prior session. Fixed via
     `Write-Host`.
  Added a `--swaddincheck` diagnostic flag to `GearGen.App` (`ISldWorks.GetAddInObject`)
  to test this against a live instance, with a same-process launch-and-poll fallback (see
  Decisions).
- `.gitignore`: added `.vs/`. Removed a stray leftover debug PNG
  (`_debug_worm_profile.png`) not referenced by anything.

## Decisions

- **Bevel gear solid is a `Compound`, not a fused `Solid`** — same call already made for
  worm gears, now made twice for the same reason: OpenCASCADE's boolean fuse is not
  trustworthy for this class of shape, tried two different fuse strategies, both failed on
  different inputs. A `Compound` of individually-correct bodies is provably manifold and
  faster besides; the cost is SolidWorks seeing a multi-body part instead of one fused
  solid, already an accepted tradeoff in this project.
- **`--swaddincheck` launches its own SolidWorks instance rather than attaching to one
  externally launched**, after `Marshal.GetActiveObject` reliably failed
  (`MK_E_UNAVAILABLE`) against an instance started by a separate tool invocation.
  Empirically, every successful COM connection this session was to an instance the same
  process either launched or was already polling — cross-process ROT visibility isn't
  reliable in this environment.
- **`SwAddin.RegisterFunction`/`UnregisterFunction` now target `Registry.LocalMachine`, not
  `CurrentUser`.** This hook only ever runs via an elevated `regasm.exe` (the non-admin
  path in `register-addin.ps1` does its own separate HKCU writes and never calls it), and
  regasm's own CLSID registration under `HKEY_CLASSES_ROOT` already requires elevation, so
  there's no non-elevated case to preserve. Changed specifically so the user's own elevated
  test (see Open threads) actually exercises the HKLM hypothesis instead of silently
  redoing the same HKCU write as before.
- **Verification method, reused deliberately from the worm/helical/bevel work earlier this
  project**: render the actual solid and measure it (`is_manifold`, body count, volume,
  addendum radius against the standard formula) rather than trusting that code which
  "looks right" and passes analytical self-tests is actually correct. Both new bevel bugs,
  and both SolidWorks registration bugs, were invisible to inspection and only surfaced by
  building the real artifact and checking it.
- **Screen capture is black in this environment** (already known for the WPF app itself);
  extended the same finding to an *external* app for the first time — `PrintWindow` with
  `PW_RENDERFULLCONTENT`, via raw Win32 handles, captures any window regardless of who
  built it, not just windows this session's own code controls.

  registration bugs fixed. Leading hypothesis: the dialog's listing scan may read only
  `HKLM:\SOFTWARE\SolidWorks\AddIns` (where the built-ins that DO appear — FeatureWorks,
  MBD, Toolbox — are registered), separate from the HKCU→HKCR COM-activation merge that
  makes direct instantiation work (confirmed working standalone). No admin rights this
  session to test it. Fixed the `RegisterFunction` hook to target HKLM and handed the user
  the exact elevated `regasm.exe ... /codebase /tlb` command to run themselves — **result
  not yet known as of this session's end.** If it works: `register-addin.ps1`'s per-user
  path may need to be retired or clearly labeled non-functional for this SolidWorks
  version. If it still doesn't show up: the cause is something this session didn't reach.
- **Environment quirk, not fully diagnosed**: a SolidWorks instance left running without
  active COM/UI interaction repeatedly self-closed within roughly a minute or two, nothing
