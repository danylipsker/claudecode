## Summary
Dany asked why Task Manager showed "SOLIDWORKS Resource Monitor" at very high power and whether the
laptop could be made silent again. The culprit is the SOLIDWORKS 2020 build of `sldProcMon.exe`: as soon
as SOLIDWORKS 2020 starts it launches the monitor, which busy-loops at ~100 % of one core and, by
design, keeps running after SOLIDWORKS closes — so it "always" burns power until killed. A second, smaller
consumer is the SOLIDWORKS Background Downloader that autostarts at every sign-in. The session ended
with a per-user watchdog scheduled task installed and verified (kills the monitor within 5 s of it
appearing), plus an optional admin script that renames the monitor away and disables the downloader
autostart; that admin step is still pending because its UAC prompt was cancelled.

## What changed
- Root cause established with measurements: the 2020 monitor pegged one core in every test (standalone
  launch while SW 2020 was open; the copy SW 2020 launched itself with `--ppid --sid`, 88 CPU-s in 90 s;
  the copy left over after a reboot, 715 CPU-s in 12 min). The 2025 and 2026 monitors exit cleanly when
  their SOLIDWORKS is not running (not tested while it is). No registry setting the binary reads changes
  the spin (tested and restored: Hide graphics card driver notifications, HeartBeatIntervalMinutes,
  Send Feedback Enabled, and the shared `HKCU\Software\SolidWorks\Diagnostics` values).
- `scripts/solidworks-monitor-watchdog.ps1`: per-user scheduled task "SOLIDWORKS Resource Monitor
  watchdog" runs the script hidden at sign-in and kills `sldProcMon.exe` every 5 s; `-Install`, `-Status`,
  `-Uninstall`; kills logged to `scripts/solidworks-watchdog.log` (git-ignored). Verified live: two
  freshly launched monitors killed after 4.6 s and 5.1 s; idle cost 82 MB RAM, no measurable CPU.
- `scripts/solidworks-quiet.ps1`: self-elevating admin script that renames `sldProcMon.exe` to
  `.disabled` in all three installs (2020, 2025, 2026) and writes the Task Manager "Disabled" value for
  the Background Downloader startup shortcut under HKLM; `-Undo` reverses, `-List` dry-runs. Not yet run.
- Memory notes saved outside the repo: the SOLIDWORKS install layout + fix, and the sandbox finding below.

## Decisions
- Watchdog (kill-on-sight) is the primary fix, not the rename: it needs no admin rights, survives
  SOLIDWORKS service-pack updates/repairs that restore the exe, and a 5 s burst per SOLIDWORKS start is
  too short to spin the fans. The rename remains available as the cleaner option.
- The watchdog lives in the repo `scripts/` folder, not `%LOCALAPPDATA%`: this session's shell is
  sandboxed and its writes outside the repo/scratchpad are virtualized — a real task process saw
  "File Not Found" for the LocalAppData copy (task exit 0xFFFD0000, and a stuck wscript.exe before that).
- The task action runs `powershell.exe -WindowStyle Hidden` directly; a wscript/VBS launcher and a
  `conhost --headless` launcher were dropped (the latter refused by the permission classifier as a
  persistence trick; direct PowerShell is the transparent choice, cost is a brief console flash at
  sign-in).
- Not done on purpose: no IFEO "Debugger" trick to block the exe by name (hacky, admin, error dialogs),
  no killing of the Background Downloader by the watchdog (single-purpose), the three "Fast Start"
  preloaders left enabled (negligible CPU).
- `.vs/` (tracked Visual Studio cache binaries) again left unstaged, matching the previous close-out.

## Follow-up in the same session (07:15–07:35)
- Dany approved the UAC prompt: `scripts/solidworks-quiet.ps1` ran elevated. All three
  `sldProcMon.exe` are now `sldProcMon.exe.disabled` (2020, 2025, 2026) and the Background Downloader
  startup entry is "Disabled" under HKLM (verified on disk and in the registry).
- The PowerShell watchdog loop kept dying with task result 0xC000013A (a console close/Ctrl+C event)
  at unpredictable moments: 26 s, ~2 min and ~8 min after start, once while the session was idle.
  Ruled out: the PT0S time limit (37 other tasks use it, some running for hours), the IgnoreNew policy
  (honoured at 07:50 with 0x800710E0), Defender (no events; only Defender + ASUS utilities installed),
  this session's tool calls (one loop survived 14 minutes of them). Cause still unknown.
- Fix: the loop now runs as `scripts/solidworks-monitor-watchdog.vbs` under wscript.exe, which has no
  console and therefore cannot receive that event; it terminates sldProcMon.exe via WMI every 5 s and
  logs each kill. Verified: a copy of the real 2020 monitor and a renamed cmd.exe were both killed
  within 3-5 s. Second layer: the task starts a new copy every 5 minutes (policy Parallel) and each
  new copy retires the older copies itself via WMI, so exactly one fresh loop is running within 5 min
  whatever happens. StopExisting was tried first and does not work here: Task Scheduler only asks the
  process to close, and a window-less wscript.exe never receives that, so copies accumulated.
  `solidworks-monitor-watchdog.ps1` is now only the installer/status tool.
