## What changed
- **Globoid wheel-space wedge centres on the centroid when the rim band grazes** (generation.py, 2f7d244): the isolating wedge was centred on the space's mid-angle at the clip rim, but near the throat the space reaches the rim only along one thin leaning finger ~4° off its body, so the wedge clipped the target and admitted a neighbour's sliver (a 2-piece section). Falls back to the piece's own centroid when the rim centre disagrees with it by more than 0.3× the wedge half-angle.
- **Globoid worm refuses a bore wider than the throat, and the card resets it** (globoid_worm.py + GearViewModel.cs, a9ca231): the hourglass worm's root narrows to ~15 mm at the throat, so a 20 mm bore inherited from a big-gear family inverted the core and OCCT threw `TopoDS::Face`. worm_core_solid now refuses with the limit named; SelectGloboidWormCard resets the inherited bore to 0 (the reset-every-shared-field rule).
- **render_globoid.py** (new, 25cfeac): shaded two-tone PNGs of the worm + throated wheel from a few angles; reused to build the animation frames.
- **Self-test `what=assembly`** (SwAddin.cs, 2e238ed): builds only the meshing assembly, used to create the globoid worm + wheel as a two-component SolidWorks assembly.
- **Regenerated the whole library**: cleared Documents\GEARS GENERATOR and re-ran all 24 families through the add-in — 24 created, 0 failed, globoid included.
- **Animation**: rendered the mesh from the real geometry (worm placed by worm_turn_deg, wheel rotated by wheel_turn_rad) frame by frame; GIF, a 550px MP4, then a 1080×1080 40-frame MP4. Installed `imageio-ffmpeg` (bundled encoder) to make the MP4s.

## Decisions
- **Two distinct globoid bugs, found by reproducing the exact params, not guessing.** The wedge-centring bug surfaced directly as `one_piece: 2 pieces`; the bore bug surfaced only through the add-in as `TopoDS::Face`. A parameter matrix passed while the add-in failed, which is what forced logging the *exact* card-sequence params (bore=20) rather than assuming.
- **The bore fix is split**: a Python refusal (defensive, so a manual oversized bore gives a clear message not a crash) plus a card reset (so the bulk run and normal card-switching always yield a buildable worm). The reset only touches the worm bore; a side effect is that families created after the globoid in the bulk run inherit bore 0 until a later card sets its own — cosmetic to a demo library.
- **Animated the geometry directly rather than through a SolidWorks motion study.** Driving SolidWorks' mate and Motion Manager APIs headlessly from here is unreliable (a normally-started SolidWorks isn't in the running-object table), so the animation is built from the same mesh relationship the tests verify. A live gear mate is left as the documented three-step manual path (float, concentric per axis, Mechanical → Gear at 10:1).

## Open threads
- **The live SolidWorks gear mate + Motion Study is not automated** — the assembly ships with the two components fixed in mesh position; the user adds the gear mate by hand (steps given). Automating it would mean driving the mate/motion API from inside the add-in, not attempted.
- **Bulk-run per-family parameters are sequence-dependent** (shared fields thread family to family), so a few library gears carry no centre bore in this batch. Not a per-family default; open any part and add one.
- **A programmatically launched SolidWorks self-closes after ~1–2 min idle** — fine when a user is interacting, awkward for headless capture (reopen from the library folder).
- Globoid tests (13) and the other wedge families' tests (29 hyperboloidal/hypoid/face) pass; no regression from the shared-code change.
